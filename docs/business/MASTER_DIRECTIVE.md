1\. MANAGER'S NON-NEGOTIABLE REQUIREMENT
----------------------------------------

The following requirement overrides any weaker database or persistence implementation described in earlier instructions.

**A single accidentally exposed database file, such as db.json, containing operational or client information is an unacceptable security failure.**

RelayOS must be designed so that its operational database is never exposed through:

*   Frontend source code.
    
*   Public static assets.
    
*   Browser-accessible directories.
    
*   GitHub repositories.
    
*   Public deployment artifacts.
    
*   Unauthenticated APIs.
    
*   Client-side local storage.
    
*   Source maps.
    
*   Application logs.
    
*   Build artifacts.
    
*   Downloadable backup files.
    
*   Debug endpoints.
    
*   Directory browsing.
    
*   Improperly configured file servers.
    

Do not solve this by hiding a file, renaming it, or adding it to .gitignore.

**There must be no JSON-file-based operational database.**

The canonical source of operational truth must be a properly configured relational database server.

This applies to development, testing, staging, demo and production environments.

JSON may be used for non-sensitive configuration, API payloads, schema definitions and clearly isolated test fixtures. It must never act as the database.

3\. DATABASE ARCHITECTURE — NO FILE-BASED OPERATIONAL STORAGE
=============================================================

3.1 PostgreSQL as the authoritative database
--------------------------------------------

Use PostgreSQL as the primary system of record.

All important operational records must be persisted in PostgreSQL.

This includes:

*   Organizations.
    
*   Users.
    
*   Roles.
    
*   Permissions.
    
*   Clients.
    
*   Contacts.
    
*   Engagements.
    
*   Outreach activities.
    
*   Consultations.
    
*   Requirements.
    
*   Decisions.
    
*   Projects.
    
*   Project phases.
    
*   Workflow definitions.
    
*   Workflow versions.
    
*   Tasks.
    
*   Modules.
    
*   Features.
    
*   Dependencies.
    
*   Milestones.
    
*   Time entries.
    
*   Risks.
    
*   Blockers.
    
*   QA reports.
    
*   Test cases.
    
*   Test results.
    
*   Handover records.
    
*   Approvals.
    
*   Exceptions.
    
*   Partners.
    
*   Partner users.
    
*   Device allocations.
    
*   Releases.
    
*   Deployments.
    
*   OTA operations.
    
*   Maintenance records.
    
*   Incidents.
    
*   Contracts.
    
*   Client updates.
    
*   Dashboard layouts.
    
*   Dashboard configurations.
    
*   Custom field definitions.
    
*   Notifications.
    
*   Automation definitions.
    
*   Automation executions.
    
*   AI recommendations.
    
*   Audit events.
    

No important project or client state may exist only inside a local file.

3.2 Database schema design
--------------------------

Use a normalized relational architecture.

Design clear domain relationships.

Use:

*   Primary keys.
    
*   Foreign keys.
    
*   Unique constraints.
    
*   Check constraints.
    
*   Non-null constraints where justified.
    
*   Proper indexes.
    
*   Composite indexes.
    
*   Appropriate timestamps.
    
*   Version columns.
    
*   Explicit deletion policies.
    
*   Referential integrity.
    

Do not depend on the frontend to enforce database integrity.

Use appropriate ON DELETE behavior.

For critical business data, prefer restricted deletion and controlled archival over cascading destruction.

3.3 Database schemas
--------------------

Organize database structures logically.

A proposed PostgreSQL schema grouping:

*   identity — users, memberships, roles and authentication references.
    
*   client — clients, contacts, engagement and consultation.
    
*   delivery — projects, phases, modules, features and tasks.
    
*   governance — policies, gates, approvals, exceptions and handovers.
    
*   quality — QA, tests, defects and reports.
    
*   partner — partner profiles, device allocations and access references.
    
*   release — build records, deployments, OTA operations and release history.
    
*   operations — maintenance, usage and incidents.
    
*   knowledge — documents, decisions and links.
    
*   workspace — dashboards, widgets, custom fields and view configurations.
    
*   automation — events, rules and executions.
    
*   audit — audit events and security records.
    

This is a logical schema organization inside the primary PostgreSQL system, not a requirement to create a separate database for every domain.

3.4 Indexing strategy
---------------------

Create indexes based on actual query patterns.

Examples:

*   Organization and workspace filters.
    
*   Client-to-project relationships.
    
*   Project status.
    
*   Task assignee and due date.
    
*   Priority and status combinations.
    
*   Phase and milestone relationships.
    
*   Pending approval queries.
    
*   Handover status.
    
*   Audit date and actor.
    
*   Notification unread state.
    
*   Searchable identifiers.
    

Use EXPLAIN ANALYZE when optimizing actual problematic queries.

Avoid indexing every column without a workload-based reason.

3.5 Transaction handling
------------------------

Use transactions for:

*   Project phase transitions.
    
*   Handover acceptance.
    
*   Ownership transfers.
    
*   Approval operations.
    
*   Scope baseline changes.
    
*   Policy publication.
    
*   Client publication.
    
*   Release transitions.
    
*   Device allocation changes.
    

A partial operation must not leave inconsistent state.

Example:

If handover acceptance updates the feature state but fails to record its approval and audit event, the transaction must roll back.

3.6 No SQLite fallback
----------------------

Do not silently replace PostgreSQL with SQLite or a JSON file when the database connection fails.

When PostgreSQL is unavailable:

*   Show a clear service-unavailable state.
    
*   Display a safe diagnostic.
    
*   Keep previously committed data intact.
    
*   Retry according to controlled policy.
    
*   Never silently switch the source of truth.
    

Use actual PostgreSQL in integration tests, not SQLite as a substitute for testing PostgreSQL-specific behavior.

4\. OTHER DATA STORES AND THEIR BOUNDARIES
==========================================

Use additional stores only for clearly defined purposes.

4.1 Redis
---------

Redis can support:

*   Caching.
    
*   Session acceleration.
    
*   Rate limiting.
    
*   Background queues.
    
*   Job coordination.
    
*   Temporary locks.
    
*   Short-lived state.
    

Redis is not the canonical database.

Important client, project, approval and task records must remain in PostgreSQL.

If Redis is lost, the application must recover its required business state from PostgreSQL.

Use appropriate expiration and invalidation.

Never cache authorization results indefinitely.

4.2 Object storage
------------------

Use private object storage for:

*   Consultation documents.
    
*   Project attachments.
    
*   QA evidence.
    
*   Handover documents.
    
*   PDFs.
    
*   Releases.
    
*   Approved exports.
    
*   Supporting media.
    

Use S3-compatible storage.

Use MinIO locally when appropriate.

Store file metadata and ownership in PostgreSQL.

Store the binary file privately outside the web root.

Never serve private attachments through a publicly exposed directory.

4.3 Document security
---------------------

Each stored file must have:

*   File ID.
    
*   Original name.
    
*   Internal storage key.
    
*   MIME type.
    
*   File size.
    
*   Uploader.
    
*   Organization ID.
    
*   Related project.
    
*   Classification.
    
*   Creation timestamp.
    
*   Integrity checksum.
    
*   Malware scan status where available.
    
*   Access permissions.
    
*   Retention status.
    

Use short-lived presigned download links after backend authorization.

Do not expose raw private storage paths.

4.4 Search
----------

Start with PostgreSQL full-text search and suitable indexes.

Add trigram search or a dedicated search engine only when justified.

Do not add Elasticsearch/OpenSearch merely to make the architecture diagram look impressive.

For AI document retrieval, use pgvector where appropriate and maintain independent record-level permissions.

A vector search result must never bypass the original document's access controls.

4.5 Analytics
-------------

Initially use PostgreSQL reporting queries and controlled read models.

A separate analytics warehouse is an optional future capability.

Do not introduce a second analytics database before there is an actual scale or reporting requirement.

5\. ABSOLUTE DATABASE EXPOSURE PREVENTION
=========================================

This section is a release-blocking security policy.

5.1 Prohibited database file patterns
-------------------------------------

Do not create operational storage files such as:

*   db.json
    
*   database.json
    
*   data.json used as a database
    
*   store.json
    
*   users.json used as a database
    
*   projects.json used as a database
    
*   clients.json used as a database
    
*   Publicly served SQLite database files
    
*   Public database dumps
    
*   Public database backups
    

Do not store serialized copies of the entire operational database in public/, static/, assets/, dist/, out/ or any other web-accessible location.

Do not put database backup or export files inside the frontend application root.

Non-sensitive build configuration JSON and clearly isolated test fixtures are allowed. They are not operational databases.

5.2 Database connection secrets
-------------------------------

The database connection string must exist only in the backend runtime's protected environment.

Example variable:

DATABASE\_URL

It must never be:

*   Hardcoded into frontend code.
    
*   Sent to a browser.
    
*   Exposed through NEXT\_PUBLIC\_ variables.
    
*   Committed to Git.
    
*   Printed in terminal logs.
    
*   Included in error responses.
    
*   Embedded in client-side source maps.
    

All connection secrets must be protected.

5.3 Public directory restrictions
---------------------------------

Use the public directory only for genuinely public assets:

*   Logos.
    
*   Public icons.
    
*   Fonts.
    
*   Public illustrations.
    
*   Public static files.
    

Never place:

*   Database data.
    
*   Private project documents.
    
*   Environment files.
    
*   SQL dumps.
    
*   Backups.
    
*   Credentials.
    
*   Session stores.
    
*   Private reports.
    

5.4 Git protection
------------------

Add appropriate protections:

*   .gitignore.
    
*   Secret scanning.
    
*   Gitleaks or an equivalent scanner.
    
*   Pre-commit checks where practical.
    
*   GitHub secret scanning where available.
    
*   Dependency auditing.
    
*   Build artifact inspection.
    

Exclude:

*   .env.
    
*   .env.\* except safe examples.
    
*   Private keys.
    
*   Database dumps.
    
*   Database storage volumes.
    
*   Local backups.
    
*   Private uploads.
    
*   Production data.
    
*   Runtime logs.
    
*   Private recordings.
    

.gitignore is not a security boundary.

It does not protect a file already committed or published.

5.5 Static exposure tests
-------------------------

Add explicit tests that:

*   /db.json returns a safe 404.
    
*   /database.json returns a safe 404.
    
*   /data.json does not expose operational state.
    
*   Common backup paths cannot be downloaded.
    
*   Private uploads cannot be accessed directly.
    
*   Directory listing is disabled.
    
*   Path traversal is blocked.
    
*   Build artifacts contain no private database files.
    
*   Frontend bundles do not contain database URLs.
    
*   Source maps do not expose secrets.
    
*   API error responses do not disclose internal SQL or file paths.
    

These tests must run automatically in CI.

5.6 If a database exposure occurs
---------------------------------

Treat accidental publication of operational database content as a security incident.

Immediately:

1.  Restrict public access.
    
2.  Identify the affected asset and exposure window.
    
3.  Revoke and rotate any exposed credentials.
    
4.  Preserve incident evidence.
    
5.  Determine what information was accessible.
    
6.  Check access logs and download history where available.
    
7.  Identify potentially affected records.
    
8.  Notify authorized security and organizational owners.
    
9.  Assess contractual and applicable regulatory notification obligations.
    
10.  Remove exposed copies and invalidate caches.
    
11.  Check Git history and build artifacts.
    
12.  Restore the correct secure storage arrangement.
    
13.  Add a regression test.
    
14.  Document the root cause and prevention.
    

Do not assume deleting the file solves a historical Git exposure or a previously cached public copy.

6\. MULTI-TENANT AND CLIENT DATA ISOLATION
==========================================

Although RelayOS is primarily internal, it manages confidential information belonging to separate clients and partners.

It must be designed to prevent one client's information from leaking into another's workspace or client portal.

6.1 Tenant and ownership boundaries
-----------------------------------

Use explicit relationships where appropriate:

*   Organization.
    
*   Workspace.
    
*   Client.
    
*   Project.
    
*   Partner.
    
*   Membership.
    
*   Resource access.
    

Every protected record must have a clearly defined ownership boundary.

6.2 PostgreSQL Row-Level Security
---------------------------------

Evaluate and implement PostgreSQL Row-Level Security for relevant tenant-scoped data.

Use this only with a correctly designed application authorization layer.

Requirements:

*   Explicit policies.
    
*   Transaction-scoped tenant context.
    
*   Runtime roles that do not bypass RLS.
    
*   Separate migration privileges.
    
*   No table-owner bypass assumptions.
    
*   Proper policies for SELECT, INSERT, UPDATE and DELETE.
    
*   Security tests for cross-tenant access.
    
*   Tests for missing or incorrect tenant context.
    

Where connection pooling is used, set and clear tenant context transactionally so context cannot leak between requests.

6.3 RBAC and ABAC
-----------------

Use both:

**RBAC:** What role does the user have?

**ABAC:** Is the user allowed to access this particular organization, project, client, document or action under the current conditions?

Check authorization on every backend operation.

A hidden UI component is not access control.

6.4 Permission tests
--------------------

Verify:

*   User A cannot access Client B's private documents.
    
*   Client viewer cannot open internal comments.
    
*   Developer cannot approve restricted handovers.
    
*   QA cannot modify security-critical permissions.
    
*   Partner A cannot read Partner B's device information.
    
*   Project membership changes take effect correctly.
    
*   A revoked user loses access.
    
*   Unauthorized file downloads fail.
    
*   AI retrieval observes the same access boundaries.
    

Never rely solely on frontend filtering.

============================================

Implement proper authentication.

Support:

*   Secure session management.
    
*   Password-based authentication where selected.
    
*   Argon2id password hashing if handling passwords directly.
    
*   Secure password recovery.
    
*   Session expiration.
    
*   Session revocation.
    
*   Login rate limiting.
    
*   Optional multi-factor authentication.
    
*   Optional OIDC/SSO integration.
    
*   Account disablement.
    
*   Device/session management.
    

Use:

*   HttpOnly cookies.
    
*   Secure cookies in production.
    
*   Appropriate SameSite settings.
    
*   CSRF protection where applicable.
    
*   Rotatable session identifiers.
    

Never store authentication tokens in localStorage.

Do not store passwords in plaintext.

Do not invent SSO availability without a configured identity provider.

For initial administrator provisioning, use a secure one-time setup process. Do not include a default production administrator password.

10\. ASYNCHRONOUS PROCESSING AND EVENT ARCHITECTURE
===================================================

*   Notifications.
    
*   Email delivery.
    
*   Large exports.
    
*   Document processing.
    
*   AI indexing.
    
*   Embedding generation.

*   Integration synchronization.

10.1 Transactional outbox
-------------------------

Implement a transactional outbox where reliable event publication is required.

The business transaction and outbox event must commit together.

A worker publishes the event.

The receiver processes it idempotently.

Do not claim exactly-once distributed execution.

Use at-least-once delivery with idempotent handlers.

10.3 Retry and dead letters
---------------------------

Use:

*   Exponential backoff.
    
*   Jitter.
    
*   Maximum attempts.
    
*   Dead-letter records.
    
*   Manual retry where authorized.
    
*   Failure reason.
    
*   Execution history.
    

Prevent endless retry loops.

10.4 Queue failure
------------------

If Redis is unavailable:

*   Preserve critical business events in PostgreSQL outbox.
    
*   Continue safe synchronous application operations.
    
*   Indicate delayed automation.
    
*   Retry after service recovery.
    

Do not lose an approved handover because notification delivery failed.

12\. BACKUP AND DISASTER RECOVERY
=================================

A database is not enterprise-ready without a recovery plan.

12.1 Backup strategy
--------------------

Use PostgreSQL-supported backup methods appropriate to the hosting environment.

Potential methods include:

*   Encrypted logical dumps.
    
*   Managed database snapshots.
    
*   Continuous WAL archiving.
    
*   Point-in-time recovery where supported.
    

Do not store backups in public application directories.

12.2 Recovery objectives
------------------------

Define:

*   Recovery Point Objective (RPO).
    
*   Recovery Time Objective (RTO).
    
*   Backup frequency.
    
*   Retention period.
    
*   Backup encryption.
    
*   Access ownership.
    
*   Restoration procedure.
    

Do not invent guaranteed RPO/RTO values.

Recommend initial values for approval.

12.3 Recovery tests
-------------------

Perform a real restoration test in an isolated environment.

Check:

*   Schema restoration.
    
*   Data completeness.
    
*   Foreign-key integrity.
    
*   Document storage references.
    
*   Workflow history.
    
*   Audit records.
    
*   Application functionality.
    
*   Authorization after restore.
    

A successful backup command is not proof that the recovery process works.

12.4 Migration safety
